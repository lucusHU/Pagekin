# 画布 P0 方案审查（2026-11-13）

审查对象：`docs/plans/canvas-mindmap-p0.md`、`docs/adr/0029-canvas-mindmap-engine-and-draft-layer.md`、`docs/plans/canvas-doc-tree-contract.md`、`docs/research/canvas-reuse-inventory.md` 与已落地的 S1/S2 代码。
参照物：用户提供的「非凡写作」（feifan.space）四张实际界面截图。

## 一、为什么现在的画布"不规整"（事实核对）

| 现象 | 事实 | 性质 |
|---|---|---|
| 节点稀疏、位置随意 | `src/components/stage/canvas/StageCanvas.tsx` 里三个节点坐标是手写的 `(220,0) / (0,140) / (440,140)` | S1 占位数据，不是产品形态 |
| 没有自动排版 | `dagre ^0.8.5` 与 `@types/dagre` 已在依赖里，但 `src/`、`electron/` 中 **0 处引用**；计划把「一键 dagre 整理」排在 **S4** | 方案排序问题：先做存储、后做观感 |
| 节点信息量低 | 节点只有一行 `label` + 上下两个连接桩；参考产品节点是多行内容卡（标题、层级、连线锚点） | 实现深度差，S3 才补节点 |
| 连线观感平 | 默认 bezier 曲线、无箭头/无正交走线；参考产品是水平向右的直角树 | 样式未调 |
| 一多就乱 | 没有层级折叠、没有等宽约束、没有 fitView padding 调优 | 缺"整齐"的结构性保证 |

**根因是定位差异，不是手艺问题。** ADR-0029 第 4 条写的是「自由拖拽 + 一键整理的混合形态」——位置是作者数据，整理是**手动触发**。参考产品是「位置由布局派生」的自动思维导图：打开即整齐，作者只改结构不改坐标。

自由画布在一屏 5 个节点时看不出差别，20 个节点时必然散。所以"不规整"是当前设计选择的直接结果，而这个选择在方案里被当成默认，没有写进验收。

## 二、底座是不是"只是工作流 + 好 UI"

分两层，结论不一样。

**硬资产确实存在**（不是套壳）：
- 领域模型：素材 → 角色名单（含身份/退休） → 世界观/大纲 → 蓝图 → 草稿版本 → 审稿 → 定稿 → 线索/伏笔 → 回收站/版本历史，落在 10 个串行迁移的 sqlite 上。
- 治理机制：生成来源绑定（`generation-source-binding`，防止 AI 输出污染事实源）、乐观锁 `sourceRevision`、`revision` 递增、坏数据隔离（`storedSnapshotInvalid`）、导出/备份。
- 这类"从设定到定稿的单一事实源 + 可回溯"在开源里不多见：`novelWriter` 偏编辑器 + 项目文件管理，Obsidian/Logseq/SiYuan 是通用笔记加插件，AFFiNE/Excalidraw/tldraw 是白板，都不承担"长篇生产链路的一致性"。

**但用户的直觉也对**：S1/S2 交付的是**通用能力**（画布引擎、文件树），任何白板/笔记产品都有；真正的差异点——事实链——在画布里只体现为 ADR 里一句"不得成为第二套事实源"。

**结构性张力（这是最该看清的一条）**：
ADR-0029 第 3 条把画布定为"作者主动草稿层，不是第二套事实源"。这保护了一致性，但代价是**画布不能承载真正的写作动作**：不能在画布上改角色卡、不能回写大纲、不能把画布当主界面。参考产品恰恰相反——它的画布、表格文件、人物档案就是数据本身（块结构 + 自动布局）。
于是：**拿画布产品的标准比，我们必然单薄；这不是实现落后，是定位给的边界。**

就画布这层单独比，也打不过 Excalidraw / tldraw / AFFiNE 这类打磨多年的白板（手势、主题、协作、插件、移动端）。不必打。要打的是"写长篇"这条链路。

## 三、方案的五个具体缺陷

1. **验收口径里没有"观感"这一项。** P0 验收门槛 4 条全是工程口径（typecheck/可逆/不泄密/单测）。UI 产品的 P0 至少要 2 条可测的视觉断言：例如"20 节点在 1440×900 内不重叠、同层水平对齐、一屏可读"、"打开画布即整齐"。
2. **切片顺序把价值放在了最后。** S1 静态占位 → S2 树 → S3 快照 → S4 布局/撤销 → S5 AI → S6 文本。前三个切片跑完，用户看到的仍是"散点 + 一棵普通树"。应改成垂直切片：一个切片内做到「打开 → 建节点 → 自动布局 → 改名 → 保存 → 重开还在 → 能拖」。
3. **定位矛盾没解。** ADR 说画布是辅助草稿，P0 却给它 6 个切片。二选一：辅助 → 砍到 2 个切片；主界面 → 必须松动 ADR-0029 第 3 条（允许节点作为角色/章节的编辑入口，写回权威仓储），否则永远是"好看的只读草稿"。
4. **复用结论没形成"不自己造"的清单。** 自写树（替代 react-complex-tree）这个决定是对的、省依赖，但同一套判断没推广到撤销栈/布局/DnD/虚拟滚动。S2 已经暴露自写的成本：代码不多，边界要自己填（回收站刷新就是实测才发现的）。
5. **设计源头文档不在仓库。** P0 计划引用 `fx1-非凡复刻与Pagekin融入架构方案.md` v0.2，但该文件不在本仓库、也不在会话目录。也就是"要复刻什么"的源头不可追溯，只剩计划里的转述——这比文档多更危险。

## 四、过程成本（"还不如直接 Cursor 规划"）

本轮实测数据：
- 代码：18 个文件改动 + 11 个新文件，`+452 / -31` 行；相关单测 26 例。
- 文档：854 行（合同 186、复用调研 212、承接快照 116、dev-notes 234、P0 计划 63、ADR 43）。
- 每次新对话的固定开销：读 5 份文档 + 核对接快照 + 跑基线检查，约 20 分钟。

文档先行的收益是"实现不跑偏"，代价是**文档里一半内容（待决项 1–7、6.1 差异表）对下一个切片没有复用价值**。对单人 fork，这套仪式偏重。建议：保留 ADR（记录不可逆决定）和一份"当前状态 + 下一步"单页，合同类文档降级为代码里的类型与测试断言——类型就是合同，测试就是验收。

## 五、三个方向与推荐

| 方向 | 内容 | 成本 | 风险 |
|---|---|---|---|
| A 收窄为辅助画布 | P0 砍到 2 个切片：树 + 画布读写 + **默认自动布局**；AI 浮层延后；差异化靠节点 `refs` 跳角色/章节 | 小（约 1 个切片） | 画布仍不是卖点 |
| B 画布升级为主界面 | 改 ADR-0029，节点即角色/章节编辑入口，写回权威仓储 | 大（3–4 个切片） | 双写一致性、与"单一事实源"冲突 |
| C 先对标再决定 | 用参考产品 5 个关键交互（自动布局 / 节点内编辑 / 表格文件 / 人物档案 / 富文本 AI）逐条打分，定 P0 取舍 | 半天 | 无 |

**推荐：先 C（半天），再按 A 落一版"打开即整齐"的画布（1 个切片），亲手拖过之后再决定要不要走 B。**
理由：现在缺的不是代码量，是"这个画布要比谁好、比什么"的判断。没有这个判断，再写 4 个切片也是同样的观感。

## 六、若继续当前路线，立即可做的三件事

1. **把布局提前到 S3，并做成默认**：`layout-tree.ts` 纯函数接 dagre，打开画布先算坐标；「一键整理」保留为手动微调后的回归动作。改动面：1 个纯函数 + `StageCanvas` + 3 条单测。
2. **节点与连线对齐参考的密度**：等宽 220–260、标题 + 可选副标题、层级左侧色条、`smoothstep` 直角连线、选中态、`fitView({ padding: 0.15 })`。
3. **视口记忆**：viewport 存进快照，重开回到上次位置；配合 S3 的快照读写一起做。

## 七、这次审查没有回答的

- 参考产品那 5 个交互各自值不值得做、做到什么程度（属于 C 的产出）。
- 画布要不要允许写回权威仓储（属于 B 的前置 ADR 决策）。
- 与高星开源项目的功能矩阵对比（需要实际拉 3–5 个项目的功能清单逐项核对，本次只做了定性判断）。
